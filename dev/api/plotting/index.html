API: Plotting

diagnostic_plot dispatches on what it is given: residuals plus an ARMA-family model produce the standard four-panel display, while a fitted GarchModel produces the six variance-model panels instead. Both return their computed values as data, so the numbers are usable with no plotting backend loaded.

TSAnalytics.diagnostic_plot — Function
diagnostic_plot(resid; fitdf=0, ppq=0, period=1, lags=nothing) -> DiagnosticPlotResult

Residual diagnostics matching the standard 4-panel display found, confirmed by reading the real source of all three, in R base's tsdiag(), astsa::sarima(), and Python's SARIMAXResults.plot_diagnostics(): standardized residuals over time, the ACF of the residuals, a normal Q-Q plot, and Ljung-Box p-values computed across a range of lags (not a single number) with a 0.05 reference line.

  • fitdf: number of estimated ARMA parameters to subtract from each Ljung-Box test's degrees of freedom (matching ljungbox_test's own argument).
  • ppq: p+q+P+Q-fixed – used only to compute the default lags count via _diagnostic_nlag (astsa::sarima's own convention); irrelevant if lags is given explicitly.
  • period: the seasonal period S, also only used by the default lags formula.
  • lags: total number of lags to show; nothing (default) uses _diagnostic_nlag(period=period, ppq=ppq, fitdf=fitdf). Ljung-Box p-values are computed for lags (ppq+abs(fitdf)+1):lags (a lag count at or below the number of already-fitted parameters gives an invalid, non-positive degrees of freedom).

Use plot(diagnostic_plot(resid)) with a Plots.jl/similar backend loaded (via the RecipesBase.jl recipe on DiagnosticPlotResult) for the actual 4-panel figure; this function itself has no plotting dependency.

Model-aware overloads diagnostic_plot(resid, m) for m::Union{ArmaModel,ArimaModel,SarimaModel} derive fitdf/ppq/period automatically from m's order/seasonal_order fields – resid still has to be supplied explicitly, since none of these model types currently store or expose fitted residuals (ArmaModel/SarimaModel keep only the fitted coefficients, not even the original series; ArimaModel keeps original_y but no direct residual accessor either) – a real, pre-existing gap in the model API noted in development-sequence.md, not something this stage silently sidesteps.

resid accepts anything tsvalues does.

Examples

julia> using TSAnalytics, Random

julia> Random.seed!(1); resid = randn(200);

julia> r = diagnostic_plot(resid);

julia> length(r.ljungbox_pvalues) == r.nlag - r.ppq
true

julia> r.nlag  # period=1 default -> _diagnostic_nlag(period=1, ppq=0) = 20
20
source
diagnostic_plot(resid, m::ArmaModel; fitdf=nothing, lags=nothing) -> DiagnosticPlotResult
diagnostic_plot(resid, m::ArimaModel; kwargs...) -> DiagnosticPlotResult
diagnostic_plot(resid, m::SarimaModel; kwargs...) -> DiagnosticPlotResult

Model-aware overload deriving ppq/period (and, unless overridden, fitdf) automatically from m's order/seasonal_order – p+q(+P+Q), and period=1 for ArmaModel/ArimaModel, period=s for SarimaModel. fitdf defaults to 0 (no fixed/constrained parameters supported by these model types), matching diagnostic_plot's own default; pass it explicitly to override. resid must still be supplied – see diagnostic_plot's own docstring for why it can't be pulled from m directly.

Examples

julia> using TSAnalytics, Random

julia> Random.seed!(1); y = randn(150);

julia> m = fit_arma(y, (1, 1));

julia> r = diagnostic_plot(randn(MersenneTwister(2), 150), m);

julia> r.ppq  # p+q = 1+1 = 2
2

diagnostic_plot(m::GarchModel; lags=nothing) -> GarchDiagnosticPlotResult

Diagnostic panels applicable to a fitted conditional-variance model. plot(diagnostic_plot(m)) renders them; the returned object holds the computed values either way, so the numbers are usable without a plotting backend – the same "return the data, not just a picture" property diagnostic_plot(resid) already has, and which R's own tsdiag does not (it returns NULL).

Which panels are drawn depends on the model: the news-impact curve is built from omega/alpha/gamma/beta for :garch and :gjr, and omitted for :egarch (see GarchDiagnosticPlotResult).

lags defaults to min(20, n÷5) for both ACF panels.

Examples

julia> using TSAnalytics, Random

julia> Random.seed!(1); e = randn(400);

julia> m = fit_garch(e, 1, 1);

julia> d = diagnostic_plot(m);

julia> length(d.std_resid) == 400
true

diagnostic_plot(m::VARModel; lags=nothing) -> VARDiagnosticPlotResult

The four-panel residual display of diagnostic_plot for every equation of a fitted VAR — standardized residuals, their ACF, a normal Q-Q plot and Ljung-Box p-values — as a K × 4 grid, one row per equation. [V] R spreads this over plot.varest and plot.varcheck; statsmodels has only its K × K plot_acorr grid.

The per-equation Ljung-Box p-values are a screening view, not the joint test: for that use portmanteau_test or var_diagnostics, which account for the cross-equation structure. Structural-stability (CUSUM) panels, which vars::plot.varstabil draws, are not implemented.

TSAnalytics.DiagnosticPlotResult — Type
DiagnosticPlotResult

Result of diagnostic_plot – the data behind astsa::sarima()'s/ SARIMAXResults.plot_diagnostics()'s standard 4-panel residual display (standardized residuals over time, ACF of residuals, a normal Q-Q plot, and Ljung-Box p-values across a range of lags). ppq is the effective lag offset actually used (ppq + abs(fitdf) from _diagnostic_nlag's own formula) – length(ljungbox_pvalues) == nlag - ppq always holds.

TSAnalytics.GarchDiagnosticPlotResult — Type
GarchDiagnosticPlotResult

Data behind diagnostic_plot(::GarchModel) – the variance-model counterpart to DiagnosticPlotResult. Carries six panels' worth of computed values; plotting them is a RecipesBase recipe, so no rendering backend is needed to produce this object.

The panel set is the applicable subset of the twelve rugarch::plot offers, restricted to what a fitted GarchModel actually carries: a conditional standard deviation against |resid|, the standardized residuals themselves, their ACF and their squared ACF (the pair that distinguishes "correlation removed" from "variance clustering removed"), a normal Q-Q plot, and the news-impact curve.

news_impact_e/news_impact_sigma2 are nothing for model=:egarch, whose news-impact curve is defined on a different (log-variance) scale and is not reduced to the same construction here rather than drawn on a silently incomparable axis.

TSAnalytics.seasonal_subseries_plot — Function
seasonal_subseries_plot(x, period) -> (values, position, cycle, means)

Data behind fpp3's own signature "subseries plot" (feasts::gg_subseries()): for each of the period positions within a seasonal cycle (e.g. each calendar month, for period=12), the subseries of x at that position across cycles, together with that position's own mean – the classic "how has each month's value moved across years" view.

position[i] is x[i]'s 1-based position within its cycle (1:period, wrapping); cycle[i] is which cycle (year) x[i] belongs to; means[p] is the mean of all values[i] with position[i] == p. Plot by grouping values by position into period panels/lines, each with a horizontal reference line at its own means[p] – deliberately a plain NamedTuple, not a dedicated result type/recipe: unlike periodogram (a single fixed display, freq vs spec), this one has no one natural rendering (panels? overlaid lines? which axis is which?), so a recipe would just be encoding one opinionated choice among several equally valid ones.

x accepts anything tsvalues does.

TSAnalytics.boxcox_profile_plot — Function
boxcox_profile_plot(x, lambdas=range(-1.0, 2.0, length=50)) -> (lambdas, loglik)

Box-Cox profile log-likelihood across candidate lambda values – the classic by-eye Box-Cox selection view (Box & Cox 1964's own derivation, as MASS::boxcox() computes it), adapted to a plain intercept-only model since boxcox isn't tied to a regression here:

loglik(lambda) = -n/2 * log(RSS(lambda)/n) + (lambda-1) * sum(log(x))

RSS(lambda) is the sum of squared deviations of boxcox(x, lambda) from its own mean; the (lambda-1)*sum(log(x)) term is the transform's log-Jacobian correction, needed to make log-likelihoods comparable across different lambda (without it, the profile would spuriously favor extreme lambda).

This ignores trend/seasonality entirely (no covariates, unlike a real MASS::boxcox() regression call) – it agrees closely with guerrero_lambda on i.i.d.-ish data (verified: both landing at the same lambda=-1 boundary on the same synthetic series), but a strongly trending/seasonal real series (e.g. AirPassengers) can show genuine, expected disagreement between the two criteria, since only guerrero_lambda accounts for the seasonal subseries structure at all.

Returns a plain (lambdas, loglik) NamedTuple, plottable directly via plot(lambdas, loglik) – deliberately no dedicated result type/recipe; unlike periodogram, there's no natural fixed display beyond "y against x", so a recipe would add a type without adding a real opinionated rendering choice worth encoding.

Examples

julia> using TSAnalytics, Random

julia> Random.seed!(1); x = abs.(randn(200)) .+ 5.0;

julia> profile = boxcox_profile_plot(x);

julia> length(profile.lambdas) == length(profile.loglik) == 50
true

julia> gl = guerrero_lambda(x, 12);

julia> peak_lam = profile.lambdas[argmax(profile.loglik)];

julia> isapprox(peak_lam, gl; atol=0.3)
true

TSAnalytics.state_decomposition — Function
state_decomposition(m) -> StateDecomposition

The decomposition of a fitted exponential-smoothing model into its state paths — observed, level, slope and seasonal — matching R's display panel for panel:

  • fit_ets (ETSModel): observed, level, slope if the trend is not :none, and season if seasonal — at most four panels. [S] That is forecast:::plot.ets exactly: its seasonal panel is the current seasonal state s1, one series, not all m seasonal states.
  • fit_tbats (TBATSModel): one season panel per seasonal period, each the period's harmonics summed through the measurement vector from the state one step back — [S] forecast::tbats.components, which plot.tbats draws. (plot.bats takes a single state per period instead; that is BATS, not TBATS.) With a Box-Cox lambda every panel, observed included, is on the transformed scale, as in R.
  • holt_winters (ExponentialSmoothingModel): the same panels, from the first observation after the season its heuristic initialization consumes.

The observed series is rebuilt from the model — fitted + resid for additive errors, fitted .* (1 .+ resid) for multiplicative ETS errors, boxcox(fitted) + resid for TBATS — so the data need not be passed back. ThetaModel keeps no state path, so it has no decomposition.

julia> using TSAnalytics, DelimitedFiles

julia> y = Float64.(readdlm(TSAnalytics.AIR_PASSENGERS, ','; skipstart=1)[:, end]);

julia> d = state_decomposition(fit_ets(y, 12; error=:mul, trend=:add, seasonal=:mul));

julia> d.observed ≈ y, d.slope === nothing, length(d.seasonal)
(true, false, 1)
source
state_decomposition(m::UCModel) -> StateDecomposition

The smoothed components of an unobserved-components model with their standard errors: level, slope (the stochastic trend's slope), the seasonal, then in extra the cycle, autoregressive, regression and irregular components, and the one-step fitted values. The recipe draws each component with a ribbon at ±1.96 standard errors – a 95% interval for the smoothed component, not a forecast interval – except the irregular, which is a residual and gets none. The standard errors are NaN over the periods the diffuse initialisation consumes, where the smoother's variance is not yet defined; the band starts after them.

julia> using TSAnalytics, DelimitedFiles

julia> nile = readdlm(TSAnalytics.NILE, ','; skipstart=1)[:, 2];

julia> d = state_decomposition(uc_local_level(nile));

julia> d.slope === nothing, first.(d.extra)
(true, ["irregular"])

julia> length(d.level) == length(d.level_se) == 100
true

TSAnalytics.StateDecomposition — Type
StateDecomposition

The fitted state paths of a model, built by state_decomposition: observed, level (nothing for a model without one), slope (nothing without a trend), and seasonal — one series per seasonal period — all on the time positions t. plot(d) draws them stacked, as R's plot.ets/plot.tbats do.

For an unobserved-components model the decomposition also carries each component's smoothed standard error (level_se, slope_se, seasonal_se; nothing where there is none), the further components in extra as (name, path, se) – cycle, autoregressive, regression, irregular – and the one-step fitted values, which the recipe overlays on the observed series. Exponential-smoothing models have no state standard errors, and their fields stay nothing/empty.

TSAnalytics.arma_roots — Function
arma_roots(m) -> ARMARootsResult

The inverse roots of the AR polynomial φ(B)Φ(Bˢ) and the MA polynomial θ(B)Θ(Bˢ) — seasonal factors multiplied out — for fit_arma, fit_arima, fit_sarima, fit_arimax and fit_sarimax models. Inside the unit circle means stationary (AR) and invertible (MA); a root near the circle is the thing to look at. [S] That is R's plot.Arima/autoplot.Arima display; Python has none.

They are the eigenvalues of the polynomials' companion matrices: for 1 − φ₁B − … − φ_pBᵖ, the roots of wᵖ − φ₁wᵖ⁻¹ − … − φ_p, and for 1 + θ₁B + … + θ_qB^q, of w^q + θ₁w^{q−1} + … + θ_q.

julia> r = arma_roots(m);

julia> length(r.ar_inverse), length(r.ma_inverse)
(1, 1)

TSAnalytics.cointegration_plot — Function
cointegration_plot(m::VECMModel) -> CointegrationPlotResult
cointegration_plot(Y, t::JohansenTest; rank=coint_rank(t)) -> CointegrationPlotResult

Each estimated equilibrium relation β'Ỹ_{t-1} over time, beside its autocorrelation function — the visual check that the relation really is stationary, which is the whole claim a cointegration test makes. [V] urca's plot for ca.jo draws the same; Python has nothing like it.

Unobserved components, factors, regimes and thresholds

The Stage 11 models plot the same way. state_decomposition and diagnostic_plot take an unobserved-components model; the rest are builders for one chart each. plot(t) draws a ThresholdTest's bootstrap distributions directly. No confidence set for a threshold is drawn: it is not computed, and a shaded region with no stated coverage would mislead. The pairwise regime-transition probabilities get no plot, for want of one natural rendering.

TSAnalytics.threshold_profile — Function
threshold_profile(m::SETARModel; criterion=:ssr) -> ThresholdProfileResult

The profile the threshold search minimised: the SSR at every candidate, or (criterion = :aic) tsDyn's AIC, n log(SSR/n) + 2k on the full series length. tsDyn's plot.selectSETAR refuses anything but the SSR; the profile is as meaningful for the AIC. With two thresholds it is the profile of the lower threshold with the upper one fixed (conditional_on), the last step of the sequential search. A threshold that was supplied, not searched, has no profile and is refused.

There is no confidence set for the threshold (Hansen 2000's likelihood-ratio inversion): it is not built, and a shaded region with no stated coverage would be worse than none.
