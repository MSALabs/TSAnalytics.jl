REAL BUG caught before shipping: an initial GJR-GARCH gamma
reparametrization used a *symmetric* cap (gamma1 = g_max*tanh(raw),
g_max=min(alpha[1], 2*(1-persistence))) -- wrongly restricting gamma1's
magnitude on BOTH sides. The true constraint (arch's own
GARCH.constraints() source) only bounds gamma1 BELOW by -alpha[1]
(alpha[1]+gamma1>=0); there is no upper-side restriction from that
constraint. The symmetric cap silently prevented the optimizer from
ever reaching gamma1 > alpha[1] -- caught immediately because Julia's
fitted gamma1 came out exactly equal to alpha1 (0.0673) instead of the
true ~0.092, on the very first real-data test run. Fixed with an
asymmetric interval via sigmoid: gamma1 in (-alpha[1],
2*(1-persistence_ab)). Re-verified: Julia now matches Python to ~1e-4
on gamma1 (0.091751 vs 0.091763) with a single start, confirmed stable
under n_restarts=8 too.

ALSO caught before shipping: the initial unpack() dispatcher for
model=:garch built the tuple in the wrong order ((mu,omega,alpha,beta,
nothing) instead of (mu,omega,alpha,nothing,beta)), silently swapping
gamma and beta for the PLAIN GARCH case during the 7.2 refactor --
caught by re-running Stage 7.1's own primary case immediately after the
refactor (optimizer failed from every start, since sigma2_of received
`nothing` where it expected beta). Confirmed the full Stage 7.1 test
suite (3535 tests, run before this refactor) still passes bit-identically
after the fix.

48-case bulk sweep (test/verification/garch/bulk_gjr_egarch/, extending

converged, mean |Julia - Python fitted param| = 6.3e-6 -- same
essentially-exact agreement as the plain-GARCH bulk sweep.
